# L340: real Dropbox folder check, 2026-10-21

**L340 remains unconfirmed.** The Dropbox client on the test Mac did not expose
the Foundation download-status/error API required to exercise the finding.
A failed restore of its online-only placeholders did succeed on the same
persisted restore after downloading the fixture through Dropbox.

## Scope

- Source tested: `4134ca1fc1fada87a1c5681cea95446c61381b66`.
- Owner authorized use of the real Dropbox account for this check.
- A new `NikoMusicHub-L340-20261021` Dropbox folder contained only a synthetic
  67-byte `.cpr` and an 8,388,608-byte binary fixture. A separate source and
  restored copy stayed under the project's ignored `dist/uat-l340-dropbox/`.
- Finder drove Dropbox's online-only/offline actions. A local Swift harness
  linked the existing `NikoMusicCore` build and used `LocalVaultRestoreEngine`,
  `SQLiteVaultTransferStore`, and the production provider-selection predicate.
  It bound writes to the fixture roots. The manifest came from the retained
  source before testing the Dropbox placeholders.
- The harness supplied fixture-only catalog binding and recorded the open
  request instead of launching a DAW on the synthetic project. This was a Core
  host integration check, not signed-app UI acceptance or a release approval.
  Real music, production settings, and the production catalog were not used.

## Observations

1. The Dropbox connector confirmed the uploaded `.cpr` and binary at 67 and
   8,388,608 bytes respectively.
2. Finder offered **Nur online**. After invoking it for the fixture only, both
   local files had zero bytes and zero allocated blocks. Finder then offered
   **Offline verfügbar machen**.
3. Foundation reported `isUbiquitousItem == false` for the Dropbox root and
   fixture. Download status and downloading error keys were absent. Promised
   metadata reported a regular file of size zero. An explicit
   `FileProviderArchiveStorage.capabilities()` call failed with
   `lookupUnavailable`; the runtime predicate selected `LocalFolderArchiveStorage`.
4. Restore refused the placeholders with `VaultManifestError.mismatch`. A
   second process retried restore `98C690B8-3BB8-4280-A640-3DA54FEF012C` and got
   the same result. The journal stayed in `materializingArchive`, with no
   permanent `failureReason`, no completed destination, and the source intact.
5. Finder downloaded the same fixture using **Offline verfügbar machen**.
   A third process retried the same restore ID and completed it. Manifest
   verification passed for the restored destination, Dropbox archive, and
   independent source. The catalog callback and open-request callback ran.
6. A fresh Dropbox metadata read confirmed the expected cloud sizes and an
   unchanged binary upload revision after the restore. The fixture was left
   downloaded for review, with its source and evidence retained locally.

## Finding status

L340 concerns a retained `ubiquitousItemDownloadingError` causing metadata
preflight to reject Retry before `startDownloadingUbiquitousItem` is called.
That key was unavailable here, so this run neither reproduces nor disproves
that condition. No production code was changed to infer cloud success from
missing metadata or to bypass manifest verification.

This host needs Dropbox to download these placeholders before Music Hub can
restore them. Automatic materialization for this configuration remains
unqualified. A client that exposes the required Foundation keys is still
needed to settle L340 after an actual failed download; do not mark it fixed
or use this record as release UAT.
