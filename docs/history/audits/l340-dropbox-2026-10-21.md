## Implementation and actual-app follow-up

The fix covers two distinct causes. Valid File Provider metadata now retains
an old downloading error as a reason to request a fresh download, instead of
throwing before Retry can start. It cannot claim fully local/current content
until the error clears; unknown metadata, changed size/type, and failed polls
still refuse success. The L340 tests exercise the actual promised-value accessor
and the request/poll path, including an error with no downloading status.

The mounted-folder adapter now detects zero-byte placeholders for positive-size
manifest entries. Its admitted materialization coordinates a read of each
expected placeholder before verifying the original manifest. Linked restores
prepare placeholders before establishing their transient inventory and fresh
content manifest. The preliminary inventory supplies progress counts before
the first asynchronous preparation; the inventory is refreshed after hydration.
Ordinary local reads retain their previous capacity behavior.

Live tests used the running SwiftUI app with a disposable bundle identity and
an isolated library/settings suite. Two synthetic projects, each with an
8 MiB binary and a small `.cpr`, were seeded as verified Vault fixtures in the
new `NikoMusicHub-L340-App-20261021` Dropbox folder. Root access was granted
through the app's own folder panels. Existing music and the production catalog
were never used. DAW handoff was disabled for the synthetic project format;
download, SQLite state, copy, verification, and UI actions were real.

- **Automatic download:** Dropbox's Finder action made the fixture files
  online-only (zero-byte local placeholders). Clicking **Restore & Open** in
  Music Hub downloaded them and reported **Restored and verified in Active
  Projects** without a manual Finder download.
- **Interrupted download:** the Dropbox main process was suspended for a
  bounded 30-second test and resumed automatically. Music Hub's **Stop Transfer**
  kept restore `AD73B95B-BF9F-4C45-9373-39DE3528A205` in `materializingArchive`,
  with `stoppedAt` set and no Active destination. After relaunch it still offered
  **Retry Restore**. The test generation was made online-only again, then that
  same Retry action downloaded and verified it to completion.
- **Failed read and retry on the final materialization code:** one fixture
  audio placeholder was temporarily held elsewhere inside the same disposable
  Dropbox folder. The app reported that downloading could not finish and offered
  **Retry Restore**. Record `301FAB9E-6A98-4512-94FE-8FA11AD32531` retained its
  manifest in `materializingArchive`, with `archiveLocalityUnavailable` and no
  permanent failure reason. Returning the original zero-byte placeholder and
  clicking **Retry Restore** completed that same ID. The app reported
  **Project Vault restore retry completed and verified**.
- All retained source, Dropbox archive, and final Active copies passed full
  manifest/hash verification. Seeded song notes, aliases, workflow stages, and
  original metadata rows were unchanged; both songs displayed **Waiting
  Feedback** and **Keep Local**. Earlier successful fixture copies were kept
  separately during repeated tests instead of overwritten or deleted.

This client still does not expose `ubiquitousItemDownloadingError`, so the live
test does not claim to have produced that SDK key naturally. The stored-error
loop is closed by deterministic regression tests; real Dropbox exercises the
coordinated-read fallback and the app's failed/stopped restore retries.
No release approval, DAW compatibility result, or remote-upload durability is
inferred from these development-app checks.
